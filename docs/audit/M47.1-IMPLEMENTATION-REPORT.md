## B. Exact Changes

### `apps/api/prisma/schema.prisma`

Targeted effective-policy correction: `DataRetentionPolicy` now includes nullable `effectiveMarker` and a composite unique constraint on `(organizationId, datasetId, effectiveMarker)`. Later runtime policy activation will set one shared marker, such as `CURRENT`, on the effective policy and leave historical policies `NULL`. PostgreSQL nullable uniqueness preserves historical versions while reserving at most one effective slot per organization/dataset.

## C. Schema

### GovernanceDataset

Platform-owned dataset catalog with:

- globally unique `datasetKey`
- display name
- optional Prisma model name
- classification tier
- deletion strategy
- retention applicability
- PII/sensitive-data flags
- metadata
- version
- active state

This model is intentionally not organization-scoped. Organization-specific policies reference it explicitly.

### DataResidencyPolicy

Organization-scoped logical policy with:

- unique organization ownership
- extensible `jurisdictionCode`
- governance residency tier
- transfer policy
- transfer configuration JSON
- version
- effective timestamp

This does not claim physical regional storage or legal compliance.

### DataRetentionPolicy

Organization and dataset-scoped policy with:

- dataset identifier
- duration in days
- explicit retention anchor
- enabled state
- metadata
- version
- effective/superseded timestamps

Uniqueness:

```text
(organizationId, datasetId, version)
```

Effective-policy uniqueness:

```text
(organizationId, datasetId, effectiveMarker)
```

Historical policies use `effectiveMarker = NULL`; the later effective policy uses one shared non-null marker.

### LegalHold

Organization-scoped hold with:

- optional governed dataset
- explicit target type
- optional target identifier
- explicit JSON coverage semantics
- active/released status
- reason/reference
- creator/releaser references
- creation/release timestamps

`BLOCKED_BY_HOLD` is a resumable DSAR state, not an irreversible terminal state.

### DsarRequest

Tenant-scoped request foundation with:

- `ACCESS`, `EXPORT`, `ERASURE` request types
- controlled lifecycle enum
- optional subject user
- optional subject reference
- requester, verifier, reviewer, approver references
- verification/review/approval timestamps
- operation-specific idempotency key
- request metadata
- failure fields
- optional hold blocker
- completion timestamp

Uniqueness:

```text
(organizationId, idempotencyKey)
```

### DsarExecutionBatch

Tenant-scoped resumable execution unit with:

- DSAR request reference
- optional dataset reference
- sequence number
- bounded total/processed counters
- retry count
- cursor JSON
- failure fields
- processing timestamps

Uniqueness:

```text
(dsarRequestId, batchSequence)
```

## D. Tenant Isolation

Every operational governance model is organization-scoped:

- `DataResidencyPolicy.organizationId`
- `DataRetentionPolicy.organizationId`
- `LegalHold.organizationId`
- `DsarRequest.organizationId`
- `DsarExecutionBatch.organizationId`

`GovernanceDataset` is intentionally platform-owned and globally identified. Tenant policy and execution records reference it through explicit foreign keys.

User references are explicit and use `SetNull` for historical actor/subject preservation where appropriate. Organization ownership uses existing `Organization` relations and `Cascade` behavior consistent with the current schema conventions.
