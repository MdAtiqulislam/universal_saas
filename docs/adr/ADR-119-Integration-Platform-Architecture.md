# ADR-119: Integration Platform Architecture

**Status:** Accepted  
**Date:** 2026-09-02  
**Milestone:** M39

## Context

The Universal Business Operations SaaS platform (M01–M38) required a dedicated integration layer to connect with external services, expose APIs to third parties, and receive webhook events from external providers. The platform required:

- Outbound webhooks to notify external systems of domain events
- Inbound webhooks to receive events from providers (e.g., payment processors, shipping carriers)
- Programmatic API access via API keys for automation and integration
- Credential storage for provider authentication
- SSRF protection for all outbound webhook endpoints

## Decision

M39 implements a dedicated `IntegrationsModule` as a cross-cutting transport and orchestration layer. Key architectural decisions:

1. **No business logic duplication**: M39 orchestrates and transports domain events generated by M01–M38. It does not own or duplicate any business entities.
2. **EventBus integration**: M39 integrates with the in-process `EventBusService` to capture domain events for outbound webhook dispatch.
3. **Dual delivery path**: Outbound webhook delivery runs through `BackgroundJob` infrastructure from M36 for resilient retry.
4. **Idempotent inbound processing**: All inbound webhook events use the M36 `IdempotencyService` to prevent duplicate processing.
5. **Tenant isolation**: All connections, API keys, webhook subscriptions, and delivery attempts are strictly tenant-scoped by `organizationId`.

## Consequences

- All M39 services depend on M36 JobService and IdempotencyService.
- Integration events are immutable once created.
- Webhook delivery is eventually consistent (not blocking domain transactions).
- API key authentication provides a dedicated external programmatic interface separate from session-based JWTs.
